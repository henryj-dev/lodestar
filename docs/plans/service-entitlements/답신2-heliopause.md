# KeyStone 팀에 — 강제 로그아웃 갭에 대한 답

답신 2026-08-06 · 원문: KeyStone `docs/plans/service-entitlements/회신2-heliopause.md`
검증: KeyStone `feat/workers-vpc-db` @ e45b80d

## 답 — 네, 메꿔 주시면 좋겠습니다. 다만 순서를 당기지는 마세요

**SET 으로 덮이지 않는 경우가 실제로 하나 있습니다.**

| 상황 | SET 이 발화하나 |
|---|---|
| 배정 회수 · 권한 강등 | 예 — 그리고 저희는 `roles: []` 를 받으면 세션을 폐기합니다 |
| **역할은 그대로인데 세션만 끊고 싶다** | **아니오** — 바뀐 것이 없으니 SET 이 나갈 이유가 없습니다 |

두 번째가 "노트북을 잃어버렸다" 입니다. 그 사람은 여전히 같은 역할의 같은 직원이고, 권한을
낮추는 것은 오히려 틀린 조치입니다. 필요한 것은 **지금 열려 있는 세션의 종료**뿐인데, 지금은
관리자가 그것을 눌러도 저희 콘솔 세션이 살아 있습니다.

그래서 "SET 은 강등, logout 은 종료라 둘 다 있는 편이 나을 수도" 라고 쓰신 것에 동의합니다.
같은 도구의 강약이 아니라 다른 도구입니다.

### 그럼에도 순서를 바꾸지는 마세요

저희에게 급한 것은 SET 쪽입니다. 관리자 역할이 회수돼도 최대 8시간 동안 **자기 플랜을 단독
승인**할 수 있는 창이 남는 것이 더 무겁습니다 — 도난당한 노트북보다 자주 있을 일이기도 하고요.

그리고 그동안 저희에게 뭉툭한 수단이 하나 있습니다. **매니저를 재시작하면 모든 세션이 사라집니다**
(세션이 메모리에 있습니다). 함대에는 영향이 없습니다 — 중계자가 계속 서빙하고 에이전트가 계속
붙습니다. 우아하지 않지만 사고 시점에 쓸 수 있는 레버가 없는 상태는 아닙니다.

## 만드신다면 — 계약을 하나 정해 주세요

실측하다 알게 된 것입니다.

```
role-change SET      sub 만 실린다 (role-change.ts:66)        → 주체 단위
back-channel logout  sid 를 실을 수 있다 (logout.ts:143)      → 세션 단위
```

**관리자 강제 로그아웃은 주체 단위여야 맞다고 봅니다.** 그 버튼의 뜻이 "이 사용자를 지금
로그아웃시킨다" 이고, 실제로 `revokeAllUserSessions` 를 부르니까요. 세션 하나만 끊는 것은 그
의도와 다릅니다.

**저희 쪽 사정도 그렇습니다: 지금 `sid` 를 저장하지 않습니다.** ID 토큰에서 `sub`·`email`·
`preferred_username`·`groups` 만 꺼내 쓰고 있습니다. 세션 단위로 오면 저장하도록 고치면 되지만,
그러면 **양쪽이 같은 것을 다르게 부르는 상태**가 됩니다 — SET 은 주체 단위, logout 은 세션 단위.

정리하면 둘 중 하나로 정해 주시면 됩니다.

- **주체 단위(권장)** — `sid` 없이 보내거나, 있어도 저희는 `sub` 로 전부 폐기합니다. SET 과 같은
  키로 다뤄지므로 저희 핸들러가 하나입니다.
- **세션 단위** — 저희가 로그인 시 `sid` 를 저장하겠습니다. 작은 변경이고, 다만 위의 이유로
  강제 로그아웃에는 안 맞는다고 봅니다.

## 나머지는 확인만

**Q3 을 3단계로 당겨 주신 것** — 그게 맞습니다. "두 키를 가정하고 만들어 달라" 는 요청이
성립하려면 계약이 먼저 나가 있어야 한다는 것, 정확히 그 이유입니다. 3단계 시점에 `entitlements`
가 항상 `[]` 인 것도 문제없습니다 — 저희는 없으면 `[]` 로 취급하는 계약을 이미 적어 뒀습니다.

**키 이름 다섯 개** — `ROLE_KEY_RE` 통과 확인 감사합니다. 그대로 확정합니다:
`site.read` · `plan.propose` · `plan.approve` · `plan.publish` · `plan.approve_own`.

**죽은 필터** — 그쪽에서 판단하시는 게 맞습니다. `revokeAssignment()` 동작 변경은 범위가 넓다는
판단에도 동의하고요.

**§8 주석** — 지금 의존이 없더라도 적어 두는 게 맞다는 데 동의합니다. 저희가 그 값을 쓰기
시작하는 시점이 그 주석이 있어야 할 시점보다 늦습니다.

## 마지막으로

2절은 **저희가 물어보지 않은 것을 확인해 주신 것**입니다. 핸드오프에서 Back-channel Logout 을
"아직 안 쓰는 것" 으로 가볍게 꼽았는데, 그걸 보고 "저 사람들이 이걸 구현하면 회수 창이 닫힌다고
기대하겠구나" 까지 읽으신 거죠. 실제로 저희는 그렇게 기대하고 있었습니다.

그리고 확인해 보니 아니었습니다. 그런 종류의 오해는 **한참 뒤에 사고로만 발견됩니다** — 관리자가
버튼을 누르고, 아무 일도 일어나지 않고, 아무도 그걸 모르는 형태로요.

4절의 *"세어 본 사람이 저인데 결론을 그쪽이 냈습니다"* 도 같은 얘기라고 봅니다. 서로 다른 각도에서
같은 코드를 보는 것이 이 왕복의 값인 것 같습니다.
