# heliopause 팀에 — sid 계약과, 그보다 먼저 말씀드릴 것

회신 2026-08-06 · 원문: `heliopause/docs/keystone-답신2.md`
근거: KeyStone `feat/workers-vpc-db` @ e45b80d 실측

---

## 먼저 — `sid` 계약을 정하기 전에 앞단이 막혀 있습니다

계약 질문에 답하려고 배선 지점을 보다가, **지금 배선해도 그쪽에 도달하지 않는다**는 걸
알았습니다. 지난 회신에서 "메꾸는 작업 자체는 크지 않다" 고 썼는데 **그 문장이 틀렸습니다.**

### 타깃 탐색이 단명 행에 묶여 있습니다

back-channel logout 은 보낼 대상을 이렇게 찾습니다:

```
getOidcBackchannelTargets()            oidc/logout.ts:54
  → oidcGrants        (sessionId 로)   :55-58
  → oidcRefreshTokens (sessionId 로, 미폐기)  :59-62
  → 둘 중 하나라도 걸린 clientId 만 대상
```

두 출처 모두 그쪽에는 없습니다.

| 출처 | 왜 없나 |
|---|---|
| `oidcGrants` | authorization code(수 분 TTL). 만료되면 GC 가 **삭제**한다 — `db/gc.ts:198` "미사용·소진 무관". Workers 에선 요청당 확률 샘플링이라 삭제 시점도 비결정적(`gc.ts:276`) |
| `oidcRefreshTokens` | `offline_access` scope 가 있어야 발급된다 — `oidc/token/+server.ts:514`. 그쪽 scope 는 `openid profile email groups` |

**즉 로그인 몇 분 뒤부터 그쪽 세션은 back-channel logout 의 타깃으로 탐색되지 않습니다.**
관리자 강제 로그아웃에 배선하든, 사용자 로그아웃 경로에서 나가든 결과가 같습니다 —
보낼 대상 목록에 그쪽이 없습니다.

### 지난번에 드린 말이 절반만 맞았습니다

회신2 에서 "back-channel logout 은 사용자 로그아웃 경로에서만 발화한다" 고 했고 그건 맞습니다.
그런데 **발화해도 그쪽에는 안 갑니다.** 저는 발화점만 보고 대상 탐색은 안 봤습니다.

그쪽이 "저희는 그렇게 기대하고 있었습니다" 라고 하신 그 기대는, 제가 정정한 뒤에도 여전히
한 겹 남아 있었던 셈입니다.

---

## 그래서 "메꾼다" 의 뜻이 달라집니다

발화점 하나 추가하는 일이 아니라 **내구성 있는 타깃 탐색을 만드는 일**입니다.

후보 둘을 보고 있습니다.

**(a) RP 세션 추적 테이블** — 토큰 발급 시 `(sessionId, clientId)` 를 남기고 세션 수명 동안 유지.
정확하지만 새 테이블 + 발급/정리 경로가 붙습니다.

**(b) 주체 단위 — `userServiceAssignments` 기반**. "이 사용자가 접근 권한을 가진 클라이언트"
전부에 보냅니다. 이미 있는 테이블이고, 배정은 세션과 무관하게 오래 삽니다.

**(b)를 유력하게 봅니다.** 그쪽이 권하신 주체 단위 의미론과 정확히 맞아떨어지기 때문입니다 —
`sub` 로 보내고 RP 가 그 사용자의 세션을 전부 폐기하는 모양이면, 애초에 세션별 타깃이 필요 없습니다.
**"어느 RP 에 알릴 것인가" 가 "이 사용자가 어느 RP 에 접근 권한을 갖는가" 로 환원됩니다.**

남은 구멍은 `allowAllUsers` 클라이언트입니다 — 배정 행 없이 접근이 허용되므로 (b)에서 누락됩니다.
착수 시점에 정하겠습니다.

---

## `sid` 계약 — 정할 필요가 없습니다. 이미 클라이언트별 설정입니다

물어보신 것에 답하면, **주체 단위 / 세션 단위는 저희가 전역으로 고르는 값이 아니라 클라이언트
등록 시 RP 가 켜고 끄는 플래그**입니다.

```
logout.ts:142    if (target.backchannelLogoutSessionRequired) {
logout.ts:143        payload.sid = idpSessionId;
```

`backchannelLogoutSessionRequired` 를 **끄면 `sid` 가 실리지 않고 `sub` 만 갑니다.** 그쪽이
원하는 주체 단위가 그대로 나옵니다. 관리 콘솔의 Back-channel Logout URI 옆 "session required"
체크박스가 그 값입니다.

그러니:

- **그쪽이 하실 것** — 클라이언트 등록/수정에서 그 체크박스를 **꺼 두시면** 됩니다. `sid` 를
  저장하실 필요 없고, 지금처럼 `sub`·`email`·`preferred_username`·`groups` 만 쓰셔도 됩니다.
- **저희가 하지 않을 것** — 전역 결정. 이미 RP 별로 갈릴 수 있게 돼 있는 것을 하나로 묶을 이유가
  없습니다.

다만 **관리자 강제 로그아웃의 의미가 주체 단위여야 한다**는 판단에는 동의합니다. 그 버튼은
`revokeAllUserSessions` 를 부르니 "이 사용자의 모든 세션" 이 맞습니다. (b) 안을 택하면 발송 자체가
주체 단위라 이 문제가 사라집니다 — `sid` 를 실을 세션이 특정되지 않으니까요.

`backchannelLogoutSessionRequired` 를 켠 클라이언트를 강제 로그아웃 경로에서 어떻게 다룰지는
그때 정하겠습니다(빈 `sid` 로 보낼 수 없으니, 세션별로 쪼개 보내거나 그 경로에선 플래그를
무시하거나).

---

## 순서 — 말씀대로 당기지 않습니다

SET 이 먼저라는 판단 그대로 갑니다. 3단계(SET 계약 확정)는 계획대로고, 강제 로그아웃 건은
별건 목록에 둡니다. 위 (a)/(b) 결정이 붙었으니 **분량이 처음 생각보다 늘었고**, 그것도 순서를
지킬 이유가 됩니다.

"매니저를 재시작하면 모든 세션이 사라진다" 는 레버가 있다고 하신 것 — 그게 있고 없고가
우선순위 판단에 실제로 영향이 있어서, 적어 주신 게 도움이 됐습니다.

## 나머지 확인

**키 이름 다섯 개 확정** — 받았습니다. 저희 쪽 설계 문서에도 그 다섯 개를 예시로 박아 두었습니다.

**죽은 필터** — 저희가 판단하겠습니다. 별건으로 추적 중입니다.

**§8 주석 — 이미 넣었습니다.** 제안하신 것보다 조금 넓게 썼습니다. 확인해 보니
`/api/totp/verify` 가 저희 자체 엔드포인트라(`src/routes/api/totp/verify/+server.ts`,
`credentials.userId` 로 조회) heliopause 를 언급할 필요 없이 계약이 내부적으로 닫히더군요.
`token/+server.ts:98` 위에 TOTP API 3종(`enroll`/`verify`/`status`)을 가리키고, 바꾸면 조용히
404 로 떨어진다는 실패 양상까지 적었습니다.

**핸드오프 §3 도 같이 넣었습니다.** `groups` 를 인가에 쓰지 말라는 문장을 네 곳에 두었습니다 —
`README.md` 클레임 절, `docs/ADMIN_GUIDE.md` scope 목록과 신설한 "발행 클레임" 절, 그리고
**관리 콘솔의 scope 입력란 바로 아래 힌트**(ko/en). 마지막 것이 "가능하면" 이라고 단서를 다셨던
자리인데, 클라이언트를 등록하는 사람이 실수 직전에 보는 자리라 넣었습니다.

## 마지막으로

이번 왕복에서 저희가 얻은 건 **"크지 않다" 고 말한 것을 실제로 열어 본 계기**입니다.
`sid` 를 어떻게 보낼지 물어봐 주셔서 배선 지점을 봤고, 보다가 배선해도 안 간다는 걸 알았습니다.
그 질문이 없었으면 만들고 나서 알았을 것이고, 그때는 **관리자가 버튼을 누르고 아무 일도
일어나지 않는** 그 형태로 발견됐을 겁니다. 답신2 마지막에 쓰신 그대로요.

이번 것은 급하지 않으니 회답 안 주셔도 됩니다. 3단계 끝나면 알려 드리겠습니다.
