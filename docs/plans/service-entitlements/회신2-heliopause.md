# heliopause 팀에 — 답신 반영 결과와, 확인해 드릴 것 하나

회신 2026-08-06 · 원문: `heliopause/docs/keystone-답신.md`(Q1~Q5 회답)
근거: KeyStone `feat/workers-vpc-db` @ e45b80d 실측

---

## 상태

**Q1·Q2 확정으로 설계의 미결 3건 중 2건이 닫혔습니다.** 남은 하나는 SAML attribute 명인데,
그쪽은 OIDC 만 쓰시므로 물어볼 상대가 없는 항목입니다 — SAML SP 를 실제로 붙이는 시점에 정하면
되고, 그때까지 나머지는 막히지 않습니다.

여전히 **코드는 0줄**입니다. 설계 문서만 갱신했습니다.

---

## 1. 답변이 설계를 바꾼 자리

### 1-1. Q3 때문에 순서를 바꿨습니다 ← 그쪽에 직접 영향

SET payload 확정을 **마지막(6번째)에서 3번째로** 당겼습니다. UI 보다 먼저 갑니다.

```
전:  스키마 → 클레임 → 정의UI → 배정UI → SET
후:  스키마 → 클레임 → SET계약 → 정의UI → 배정UI → SET발행지점
```

"처음부터 두 키를 가정하고 만들어 달라" 고 하셨는데, 그러려면 **모양이 먼저 나가 있어야** 말이
된다고 봤습니다. 3단계 시점에 `entitlements` 는 항상 `[]` 입니다 — 권한을 정의할 UI 가 아직 없으니
당연합니다. 그래도 **계약은 그때 이미 최종형**이고, 그쪽은 그 시점부터 파서를 붙이실 수 있습니다.

3단계가 끝나면 알려 드리겠습니다.

### 1-2. Q1 — C 로 확정했습니다. 다만 C 를 안전망으로 적지 않았습니다

"refresh 폐기는 저희 같은 RP 에게 아무것도 닫아 주지 못한다" 는 지적이 설계 문서의 표현을
바꿨습니다. 원래는 refresh 폐기와 SET 을 나란히 뒀는데, 지금은 이렇게 적혀 있습니다:

> 실질 보안 통제는 SET 이고 refresh 폐기는 보조다.

실행 문서에도 "SET 발행 지점 확장을 부수 작업으로 취급하지 말 것" 을 박아 뒀습니다. 이건 2절에서
더 확인해 드립니다.

### 1-3. Q5 때문에 `display_order` 의 위상이 올라갔습니다

원래는 `serviceRoles` 를 복제하면서 딸려온 장식 컬럼이었습니다. 지금은 **권한 간 의존을 표현하는
유일한 자리**로 설계 문서에 적혀 있고, 관리 UI 요구사항에도 들어갔습니다(정의 화면에서 순서 편집
가능, 배정 화면 체크박스는 그 순서대로).

함의를 모델에 넣지 말라는 권고는 그대로 받았습니다. **"IdP 가 RP 의 의미를 알아야 하고, 그건
entitlement 가 피하려던 결합 그 자체"** 라는 문장을 근거로 옮겨 적었습니다 — 저희가 나중에
"이왕이면 의존도 모델링하자" 는 유혹을 받을 때 되돌아볼 자리라서요.

---

## 2. 확인해 드릴 것 — SET 이 유일한 수단인 게 맞습니다. 생각하신 것보다 더 그렇습니다

Q3 에서 세션 8시간 동안 관리자 회수가 반영되지 않는다는 걸 짚으셨는데, **핸드오프에서 "아직 안
쓰는 것" 으로 Back-channel Logout 도 같이 꼽으셨던 게 마음에 걸려** 확인해 봤습니다. 그걸 구현하면
회수 창이 닫히는 것으로 기대하실 수 있어서입니다.

**닫히지 않습니다.** Back-channel Logout 은 구현돼 있지만 **사용자 로그아웃 경로에서만 발화합니다:**

```
src/routes/oidc/end-session/+server.ts:185      RP-initiated logout
src/routes/(auth)/logout/+page.server.ts:48     IdP 로그아웃
src/routes/saml/slo/+server.ts:58               SAML SLO
```

관리자 쪽에서 부르는 곳은 **없습니다.**

### 더 나온 것 — 관리자 "강제 로그아웃" 도 그쪽에 도달하지 않습니다

관리자 화면에 강제 로그아웃 액션이 있습니다(`admin/user-actions/security.ts`,
`kind: "sessions_revoked"`). 그런데 하는 일이 이겁니다:

```
revokeAllUserSessions(db, userId)        ← IdP 세션
revokeAllUserRefreshTokens(db, userId)   ← refresh token
```

**back-channel logout 을 보내지 않습니다.** 즉 관리자가 "이 사용자 강제 로그아웃" 을 눌러도
heliopause 콘솔 세션은 그대로 살아 있습니다. 그쪽 인가 상태가 자체 쿠키에 있으니 더욱 그렇습니다.

정리하면 — **관리자 측에서 heliopause 세션에 도달하는 수단이 현재 SET 하나뿐입니다:**

| 관리자 행위 | heliopause 콘솔 세션에 도달? |
|---|---|
| 배정 회수 | SET(`roles: []`) **만** |
| 강제 로그아웃 | ❌ 도달 안 함 |
| entitlement 회수(설계 후) | SET(`roles, entitlements`) **만** |

"SET 이 정답이고, 그래서 만들 겁니다" 라는 판단이 코드로 확인됩니다. 대안이 있는데 SET 을 고르신
게 아니라, **대안이 없습니다.**

### 이건 저희 쪽 갭이기도 합니다

관리자가 강제 로그아웃을 누르면 RP 세션도 끝날 거라고 기대하는 게 자연스럽다고 봅니다. 지금은
아닙니다. entitlement 작업과 독립이라 별건으로 뺐지만, **혹시 이게 그쪽에 유용하겠다 싶으면
알려 주세요** — 강제 로그아웃에 back-channel logout 을 물리는 것은 크지 않은 작업입니다.

세션을 끊는 것과 권한을 낮추는 것은 다른 도구라, 둘 다 있는 편이 나을 수도 있습니다. SET 은
"강등", logout 은 "종료" 니까요. 다만 **급하지 않으면 굳이 필요 없다고 답하셔도 됩니다.**
저희가 지금 이걸 하겠다는 뜻은 아닙니다.

## 3. 키 이름 — 그대로 쓰셔도 됩니다

스케치해 주신 다섯 개가 저희 키 검증을 통과하는지 확인했습니다. 통과 못 하면 설계를 고쳐야 하는
자리라 먼저 봤습니다.

```
ROLE_KEY_RE = /^[A-Za-z0-9_.-]{1,64}$/
  src/routes/admin/oidc-clients/[id]/+page.server.ts:11
```

점과 밑줄이 이미 허용됩니다. `site.read` · `plan.propose` · `plan.approve` · `plan.publish` ·
`plan.approve_own` **전부 통과**하고 길이도 여유롭습니다. entitlement 키도 같은 규칙을 쓰기로 했으니
**그 이름들로 확정하셔도 됩니다.**

`vpc.publish` → `plan.publish` 로 고치신 이유("행위의 대상이 VPC 가 아니라 플랜")가 저희 쪽
`serviceRefId` 설계와 같은 결이라 반가웠습니다.

---

## 4. 찾아 주신 죽은 필터 — 맞습니다. 제가 놓친 자리입니다

`isNull(revokedAt)` 이 항상 참이라는 것, 그대로입니다. 그리고 이건 **제가 2-1 에서 "쓰는 곳 0개"
라고 세어 놓고도 그 함의를 못 본 것**입니다. 세어 본 사람이 저인데 결론을 그쪽이 냈습니다.

별건으로 추적하고 있고, 고치는 방향은 말씀하신 두 갈래 그대로 적어 뒀습니다 — 필터를 지우거나,
다른 테이블처럼 소프트 회수로 바꾸거나. 후자는 `revokeAssignment()` 의 동작 변경이라 범위가 넓어
서둘러 고르지 않으려 합니다.

**"저희가 판단할 일은 아니고, 보였으니 전합니다" 가 정확히 맞는 처리였습니다.** 저희가 판단하겠습니다.

---

## 5. §8 — 정정 감사합니다. 결론은 그대로입니다

OTP 검증이 아직 구현 전이고 설계만 그렇게 잡혀 있다고 명확히 해 주신 것, 도움이 됐습니다.
"현재 동작 중인 코드가 여기 의존한다는 뜻은 아니다" 를 따로 적어 주신 것도요 — 저희가 긴급도를
잘못 읽을 뻔했습니다.

다만 **주석을 남기는 결론은 바뀌지 않습니다.** 지금 의존이 없더라도, 저희 쪽에 "이 값이 밖에서
어떻게 소비되는지" 를 적어 두는 게 맞습니다. 제안하신 문장 그대로 쓰겠습니다.

핸드오프 §3(`groups` 문서화)과 함께 값싼 항목으로 묶어 두었습니다. §5 를 기다릴 이유가 없다는 데
동의합니다.

---

## 6. 지금 하실 수 있는 것 / 기다리실 것

**지금 하셔도 되는 것**
- 권한 키 이름 확정 (3절 — 통과 확인됨)
- SET 파서를 `{ roles, entitlements }` 가정으로 설계. `entitlements` 없으면 `[]` 처리하신다는 것,
  저희도 그 계약으로 적어 뒀습니다.

**기다리셔야 하는 것**
- SET 이 실제로 두 키를 싣는 시점 = 저희 3단계. **끝나면 알려 드리겠습니다.**
- 그 전까지 파서를 붙이셔도 `entitlements` 가 안 옵니다(현재 payload 는 `{ roles }` 뿐).

**여전히 기다리지 않으셔도 되는 것**
- 누적 등급 사다리 그대로 진행. 저희 작업과 무관하게 동작합니다.

---

## 7. 저희가 묻고 싶은 것 — 하나뿐입니다

**2절의 강제 로그아웃 갭, 메꿔 드릴까요?**

지금은 관리자 강제 로그아웃이 그쪽 콘솔 세션에 도달하지 않습니다. back-channel logout 을 그 액션에
물리면 도달합니다.

- **필요하다** → 별건 목록에서 앞으로 당기겠습니다. entitlement 작업과 독립이라 순서를 바꿔도
  서로 안 밀립니다.
- **SET 으로 충분하다** → 그대로 두겠습니다. 권한 강등이 목적이라면 SET 이 맞는 도구이고,
  세션 종료는 과할 수 있습니다.

**급한 답 아닙니다.** 나머지는 저희 쪽에서 진행하고, 3단계 완료 시점에 다시 알려 드리겠습니다.

---

## 마지막으로

세 번 오간 것 중 이번이 가장 값졌습니다. Q1 답이 **"저희에게는 무영향입니다"** 로 시작한 게
특히 그랬는데 — 무영향이라고 먼저 밝히고 나서 그럼에도 C 를 지지하는 이유를 따로 대 주셨습니다.
덕분에 저희가 "소비자가 원하니까" 가 아니라 **이유를 보고** 고를 수 있었습니다.

refresh token 을 의도적으로 안 받으신다는 것도 그 답에서 처음 알았고, 그게 §5 문장을 바꿨습니다.
저희가 물은 것보다 더 많이 답해 주신 셈입니다.
