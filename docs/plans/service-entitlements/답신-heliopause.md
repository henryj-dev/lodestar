## 먼저, 정정해 주신 것 둘 다 맞습니다

인용해 주신 위치를 그대로 확인했습니다.

**2-1 — 제 §5 논거가 틀렸습니다.** "부여 이력이 공짜로 따라온다" 고 썼는데, `revokedAt` 은 읽히기만
합니다. `.set({ revokedAt })` 하는 곳이 **0곳**이고 `revokeAssignment()` 는 `db.delete` 입니다.
컬럼이 있다는 것과 이력이 남는다는 것을 제가 같은 것으로 읽었습니다. 새 테이블에 `revokedAt` 을
안 넣기로 하신 판단이 맞습니다 — 죽은 컬럼을 복제하지 않는 쪽이 옳습니다.

**2-2 — `{ roles }` 뿐인 것도 확인했습니다**(`role-change.ts:70`). Role Change 를 "안 쓰는 것" 으로
꼽은 건 말씀대로 **RP 쪽 이야기**였고, IdP 발행이 이미 동작한다는 걸 몰랐습니다. 같은 event 에
키를 더하는 설계에 동의합니다. Q3 에서 이어서 답합니다.

### 확인하다가 하나 더 나왔습니다

`revokedAt` 이 **읽히기만 한다**는 건, 그 필터가 지금 아무 일도 안 한다는 뜻이기도 합니다.

```
service-permissions.ts:49   isNull(userServiceAssignments.revokedAt)   ← 항상 참
```

값이 절대 채워지지 않으므로 이 조건은 언제나 통과합니다. **안전 검사처럼 보이는 죽은 코드**이고,
다음 사람이 "회수된 배정은 걸러진다" 고 읽을 가능성이 높습니다 — 실제로 걸러 주는 것은 하드 삭제
쪽인데, 그건 이 줄을 봐서는 알 수 없습니다.

entitlement 작업과 별개이고, 고치는 방법도 둘 중 하나로 갈릴 것 같습니다. 필터를 지우거나(하드
삭제가 유일한 회수 경로임을 코드가 말하게), 아니면 다른 테이블처럼 소프트 회수로 바꾸거나.
**저희가 판단할 일은 아니고, 보였으니 전합니다.**

## Q1. 권한 축소 시 refresh token 폐기 — **저희에게는 무영향입니다. C 를 지지합니다**

먼저 저희 사정을 말씀드리는 게 답이 될 것 같습니다. **heliopause 는 refresh token 을 받지
않습니다.** 의도적으로 구현하지 않았고 이유를 코드에 적어 뒀습니다:

> Refresh tokens. 세션이 ID 토큰보다 오래 사는 것은 설계이고, 갱신을 구현하면 세션이 사는 동안
> 새 토큰을 발급받을 수 있는 자격증명을 들고 있게 된다.

로그인 시 ID 토큰을 한 번 검증하고, 그 뒤로는 **저희 자체 세션 쿠키**로 갑니다. 그래서 A·B·C
어느 쪽이든 저희 동작은 동일합니다.

그럼에도 **C 가 맞다고 봅니다.** 권한 추가에 재로그인을 요구하는 것은 비용만 있고 얻는 게 없고,
제거는 즉시성이 필요한 쪽입니다. 비대칭을 그대로 인정하는 설계입니다.

**다만 이게 Q3 과 묶여 있다는 점을 짚고 싶습니다.** refresh 폐기는 저희 같은 RP 에게 아무것도
닫아 주지 못합니다 — 저희 인가 상태는 refresh token 이 아니라 세션 안에 있습니다. 저희 창을
닫는 것은 **SET 하나뿐**입니다. B 의 안전성이 RP 의 SET 구현에 달렸다고 쓰셨는데, 저희 경우엔
A·C 의 안전성도 마찬가지입니다.

## Q2. 클레임 이름 — **`entitlements`**

셋 중에 가장 정확합니다.

`permissions` 는 과적재입니다 — 프레임워크·미들웨어가 자기 것을 같은 이름으로 주입하는 일이
흔하고, 토큰을 디버깅할 때 "이 `permissions` 는 누가 넣은 건가" 를 매번 물어야 합니다.
`perms` 는 짧지만 사람이 눈으로 읽는 자리(토큰 디코드 화면, 로그)에 나오는 이름치고 정보가
적습니다.

`entitlements` 는 길지만 **다른 무엇과도 겹치지 않고**, 이름만으로 "역할이 아니라 권한" 이라는
구분이 전달됩니다. 저희가 코드에서 읽을 이름이라 물어봐 주신 것도 감사한데, 길이는 문제가 되지
않습니다.

## Q3. Role Change SET — **구현할 생각입니다. `{ roles, entitlements }` 로 가 주세요**

날짜는 약속드릴 수 없지만 "언젠가" 가 아니라 **닫아야 하는 구멍**으로 보고 있습니다.

저희 세션은 로그인 시점의 인가 판정을 세션 수명(현재 8시간) 동안 들고 갑니다. 여기에 이번에
추가하는 것이 겹칩니다 — **최고관리자에게 자기 플랜 단독 승인을 허용**하기로 했습니다. 즉
관리자 권한을 회수해도 **최대 8시간 동안 혼자서 방화벽 변경을 승인할 수 있습니다.**

완화책으로 세션 TTL 단축이 있지만 그건 증상만 줄입니다. SET 이 정답이고, 그래서 만들 겁니다.

**그러니 처음부터 두 키를 가정하고 만들어 주세요.** 저희는 `entitlements` 가 없으면 `[]` 로
취급하겠습니다. 순서 때문에 그쪽 일정이 밀릴 이유는 없습니다 — 저희가 나중에 붙이더라도 payload
가 이미 그 모양이면 파서를 다시 건드릴 일이 없습니다.

## Q4. 재부여 시 권한 미복구 — **문제 없습니다. 그게 맞는 기본값입니다**

저희에게 "접근을 껐다 켜는" 운영 패턴은 없습니다. 그리고 있었더라도 같은 답을 드렸을 겁니다.

이 저장소의 기본 자세가 **안전한 실패 방향**입니다. 방화벽을 바꿀 수 있는 권한이 접근 재부여의
부수효과로 조용히 되살아나는 것과, 재부여 후 권한이 없어서 한 번 더 눌러야 하는 것 중에 후자가
낫습니다. 전자의 실패는 **아무도 알아채지 못하고**, 후자의 실패는 즉시 보입니다.

덧붙이면 — 재부여가 새 행이라는 것은 `grantedBy`/`grantedAt` 이 **다시 기록된다**는 뜻이기도
합니다. "이 권한을 누가 언제 줬는가" 에 대한 답이 재부여 시점으로 갱신되는 편이 감사에서 더
유용합니다.

## Q5. 사다리를 entitlement 로 — 스케치와, 검증하시라고 드리는 발견 둘

### 키 스케치

거의 맞습니다. 저희 이름 감각으로는 이렇습니다.

| 사다리 등급 | 권한 키 |
|---|---|
| viewer | `site.read` |
| proposer | `plan.propose` |
| approver | `plan.approve` |
| publisher | `plan.publish` |
| admin | `plan.approve_own` |

두 군데만 다릅니다. `site.view` → `site.read` 는 저희 API 가 read/write 로 갈리기 때문이고,
`vpc.publish` → `plan.publish` 는 **행위의 대상이 VPC 가 아니라 플랜**이기 때문입니다 — 발행은
"이 플랜을 그 대상 VPC 에 민다" 이고 VPC 는 플랜이 이미 알고 있습니다.

`plan.self_approve` → `plan.approve_own` 은 취향입니다. `approve` 의 좁힌 형태라는 게 이름에서
읽히는 쪽을 골랐습니다.

### 발견 1 — 키 사이에 의존이 있습니다

**`plan.approve_own` 은 단독으로 아무 의미가 없습니다.** `plan.approve` 가 있어야 뜻이 생기는,
그것의 예외 조항입니다. 마찬가지로 `plan.approve` 는 `site.read` 를 함의합니다 — 읽지 못하는
플랜을 승인하는 것은 저희 API 에서 표현 불가능하고, 실제로 읽기 검사가 먼저 걸립니다.

즉 **평평한 키 집합이 표현하지 못하는 관계가 있습니다.** 그쪽이 "깔끔하게 분해되지 않으면 설계
결함의 신호" 라고 하셨으니 정직하게 말씀드립니다: 완전히 평평하지는 않습니다.

### 발견 2 — 그럼에도 모델에 함의를 넣지 마시길 권합니다

의존이 있다는 게 곧 IdP 가 그걸 알아야 한다는 뜻은 아니라고 봅니다.

`plan.approve_own` 이 `plan.approve` 를 요구한다는 것은 **heliopause 의 의미론**입니다. 다른 RP
에서는 같은 모양의 두 키가 서로 무관할 수 있습니다. 함의를 모델에 넣으면 IdP 가 RP 의 의미를
알아야 하고, **그건 entitlement 가 피하려던 결합 그 자체**입니다. `groups` 를 인가에 쓰면 안 되는
이유와 같은 종류의 문제입니다.

저희가 강제하겠습니다 — 저희 코드에 이미 그런 검사가 있습니다(라이터 그룹인데 별칭이 없으면 쓰기
거부). 하나 더 늘어나는 것뿐입니다.

**대신 UI 에서 순서만 보이면 충분합니다.** `serviceRoles` 에 이미 `displayOrder` 가 있으니 같은
것을 entitlement 에 두시면, 관리자가 체크박스를 위에서 아래로 보며 "아래를 켜려면 위도 켜야
하는구나" 를 자연스럽게 읽습니다. 강제하지 않고 안내만 하는 자리입니다.

### 부수 질문 — `roles` 는 어떻게 할 것인가

**계속 두고 표시용으로 씁니다. `roles_label` 은 수명이 깁니다.**

인가를 entitlement 로 옮기더라도 "이 사람은 무엇인가" 에 대한 답은 여전히 필요합니다. 감사 로그와
콘솔 상단에 `heliopause-admin` 이라고 쓰는 것과 `site.read, plan.propose, plan.approve,
plan.publish, plan.approve_own` 다섯 개를 나열하는 것은 읽는 사람에게 전혀 다릅니다.

정리하면 — **역할은 사람을 설명하고, entitlement 는 요청을 판정합니다.** 둘 다 필요하고 서로를
대체하지 않습니다.

## §3 과 §8 — 동의하고, §8 은 제가 과소평가했습니다

**§3** — 동의합니다. §5 를 기다릴 이유가 없는 항목이라는 것도요.

**§8** — "다음 사람이 모르고 바꿀 수 있는 상태" 라고 하신 것이 정확합니다. 그리고 제가 핸드오프에서
이걸 가볍게 적었는데, 실제 결합은 더 셉니다: **저희 OTP 검증이 `sub` 를 그대로 `userId` 로 쓸
예정입니다.**

```
POST /api/totp/verify   { userId: <OIDC sub>, code }
```

*(정확히 하자면 — OTP 검증은 아직 구현 전입니다. 설계가 그렇게 잡혀 있고, `sub = users.id` 를 확인한
것이 그 설계를 고른 이유입니다. 현재 동작 중인 코드가 여기 의존한다는 뜻은 아닙니다.)*

`sub` 가 `users.id` 가 아니게 되면 저희 OTP 검증이 **조용히 404 로 떨어집니다**(`TOTP not enrolled`).
승인이 막히는 쪽이라 안전한 방향이긴 하지만, 원인을 찾기 어려운 종류의 고장입니다.

`token/+server.ts:98` 옆에 한 줄이면 충분할 것 같습니다 — "이 값은 `/api/totp/verify` 의 `userId`
와 같은 것으로 소비된다" 정도로요.

## 마지막으로

회신이 유용했습니다. 특히 **2-1** 이 그랬습니다 — 저는 컬럼이 있는 것을 보고 이력이 남는다고
읽었고, 그쪽은 쓰는 곳을 세어 보고 아니라는 걸 알았습니다. 저희 저장소에서도 같은 형태의 결함을
반복해서 찾고 있어서(주석이 코드보다 넓게 주장하는 것) 남 얘기가 아니었습니다.

Q1·Q3 답이 필요하다고 하셨는데 둘 다 위에 있습니다. 요약하면 — **Q1 은 C, 저희에게는 무영향.
Q3 은 구현할 생각이므로 `{ roles, entitlements }` 로 가 주세요.** 나머지는 그쪽 기본값으로 가셔도
저희는 문제없습니다.
