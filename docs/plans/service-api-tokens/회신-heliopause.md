## 2. §2-1 이 실제보다 약하게 적혀 있습니다

이게 이 회신에서 가장 중요한 부분입니다.

문서는 "성공 호출이 dispatcher 것인지 heliopause 것인지 구별할 방법이 없다" 고 하셨는데,
확인해 보니 **다섯 엔드포인트 어디에도 성공 감사가 없습니다.**

```
/api/totp/verify          감사 없음
/api/totp/status          감사 없음
/api/totp/enroll/init     감사 없음
/api/totp/enroll/confirm  감사 없음
/api/users/lookup         throttle 초과(실패)만 기록
```

`requireServiceToken()` 은 성공하면 조용히 반환하고(`service-token.ts:20-35`), 라우트 쪽에도
성공 감사가 없습니다. 즉 **호출자를 구분 못 하는 게 아니라 행 자체가 남지 않습니다.**

`/api/totp/verify` 성공은 그쪽에서 방화벽 변경 승인의 2단계 검증입니다. 사고 조사에서
"이 사람의 OTP 가 언제 검증됐는가" 를 물으면 지금은 **"기록이 없다"** 가 답입니다.
"서비스 토큰을 가진 누군가" 보다 한 칸 더 나쁩니다.

### 이건 토큰 모델과 무관하게 오늘 고칠 수 있습니다

스코프도 테이블도 UI도 필요 없습니다. 성공 경로에 감사 한 건을 남기면 됩니다 —
`recordAuditEvent` 는 이미 `userId`·`kind`·`outcome`·`ip`·`userAgent`·`detail` 을 받습니다.

```
kind: "service_totp_verified"   outcome: "success"   userId: <검증 대상>
```

호출자 구분은 여전히 안 되지만, **"누구의 2단계가 언제 검증됐는가" 에는 답할 수 있게 됩니다.**
그쪽이 §2-1 에서 실제로 필요하다고 한 것의 절반이 여기 있고, 나머지 절반(호출자 신원)은 4절이
채웁니다.

**이건 저희가 할 일입니다.** 별건으로 올려 두겠습니다.

## 3. 사소한 정정 둘

**`service-token.ts` 의 감사 호출은 두 곳이 아니라 한 곳입니다**(`:48`). 결론은 오히려
강해집니다 — 실패 경로에도 감사가 하나뿐이고 성공 경로엔 없습니다.

**`/api/users/lookup` 에는 이미 열거 상한이 있습니다.** ctrls M-9 로 IP당 분당 제한이 걸리고
초과 시 `service_lookup_throttled` 감사가 남습니다(`lookup/+server.ts:51-58`). 3절에서 감수
가능하다고 하신 "사용자 조회" 노출은 무제한 덤프가 아니라 상한이 걸린 조회입니다 — 판단이
바뀌지는 않겠지만 정확한 그림을 위해 적습니다.

---

## 4. 중간안 — UI 없이 셋 중 둘을 닫습니다

4절 제안(테이블 2개 + 발급 UI)에 동의합니다. 다만 그 설계에서 **"UI 가 절반 이상" 이라 착수가
무겁다**는 것도 그대로입니다. 그래서 중간 단계를 제안합니다.

**핵심은 라우트에서 보이는 API 가 두 설계에서 똑같다는 것입니다.**

```
requireServiceToken(event, "totp.verify")
```

이 시그니처는 스코프를 **DB 에서 읽든 설정에서 읽든 동일**합니다. 그러니 먼저 설정 기반으로
만들어도 나중 버려지는 코드가 없습니다 — 라우트 5곳의 스코프 이름이 그대로 남고, 뒤에
테이블·UI 를 붙일 때 해석기만 바뀝니다.

설정 기반 1단계:

```
DISPATCHER_SERVICE_TOKEN   기존 토큰 = 전 스코프 (dispatcher 무중단)
SERVICE_TOKENS             [{ name, token, scopes[] }, ...]  ← 호출자별
```

| 그쪽 우려 | 1단계로 닫히나 |
|---|---|
| 2-3 최소권한 | **닫힘** — heliopause 토큰에 `totp.verify` 만 |
| 2-2 회전 | **닫힘** — 호출자별로 독립 회전 |
| 2-1 호출자 신원 | **닫힘** — 매칭된 토큰의 `name` 을 감사에 남길 수 있음 |
| 발급/폐기 셀프서비스 | 안 닫힘 — 배포가 필요(2단계에서 UI) |

즉 **호출자가 셋째가 되기 전에 필요한 것**은 1단계로 거의 다 됩니다. 남는 것은 "UI 없이
env 를 고쳐 배포해야 한다" 인데, 호출자가 둘셋인 동안은 그게 실질 문제가 아닙니다.

이렇게 쪼개면 2단계(테이블 + UI)는 **급하지 않은 편의 개선**이 되고, 미뤄져도 보안 상태가
나빠지지 않습니다. 지금 구조는 미뤄지면 계속 과권한입니다.

**아직 확정 아닙니다** — entitlement UI 를 끝내고 다시 보겠습니다.

---

## 5. 그쪽 §6 에 대해

토큰을 env 대신 파일로 마운트하신다는 것, 맞는 판단이라고 봅니다. 저희 쪽은 Workers 경로에서
secret 이 env 로 들어오는 구조라 같은 선택지가 없지만, 그쪽 통제 안에서 줄일 수 있는 것을
줄이신 것으로 읽었습니다.

"스코프를 강제하는 것이 저희 코드뿐" 이라고 쓰신 것도 정확합니다. 그게 저희 쪽 결함이고
그쪽 규율로 메우고 계신 상태입니다 — 4절 1단계가 그걸 저희 쪽으로 되가져오는 일입니다.

## 6. entitlement 쪽 진행 (첫 핸드오프 후속)

별건이지만 같이 알립니다. **P1~P3 완료, 브랜치 `feat/service-entitlements`.**

- 스키마 2테이블 × 3방언 (마이그레이션 생성·적용 완료)
- `entitlements` 클레임이 id_token·userinfo 에 발행. **권한 0개면 키를 아예 생략**하므로
  지금 그쪽 토큰은 바이트 단위로 이전과 동일합니다.
- **SET payload 가 `{ roles, entitlements }` 로 나갑니다.** 지금 파서를 만드셔도 됩니다.
  현재 관리 액션 경로에서는 `entitlements` 가 항상 `[]` 입니다(권한 부여 UI 가 아직 없어서).
  키는 항상 실리므로 없으면 `[]` 로 취급하시면 되고, 그 계약은 확정입니다.

남은 것은 UI 3페이즈입니다. 그리고 Q2 때 확인해 드린 키 이름 다섯 개는 그대로 통과합니다 —
`ROLE_KEY_RE` 를 entitlement 키 검증에도 그대로 씁니다.
